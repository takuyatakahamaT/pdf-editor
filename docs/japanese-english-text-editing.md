# 日本語・英語の文字編集設計

更新日: 2026-10-30。初期調査は[混合方式ADR](hybrid-text-editing-adr.md)に保存する。

## 利用者の操作

文字を選択し、入力し、確定する。書体と文字サイズは必要なときだけ変更する。「PDF内部」「上塗り」「非対応構造」のような方式選択・常設説明は置かない。処理が失敗した場合は入力と既存の編集を残し、短いエラーだけを伝える。

対象は日本語と英語の横書き文書。単なる数字変更でも書体・太さ・文字サイズ・ベースラインを維持すること、背景・罫線・未編集文字を巻き込まないことを優先する。長い文章の自動段落組版より、既存文書の局所編集を先に安定させる。

## 内部の責務

- `PDFGlyphIndex`が視覚上の選択と元PDFの文字情報を結び付ける。Unicodeだけでなくページ・座標・フォント・文字送り・描画状態も照合する。同じ文言が別の場所にあることだけを理由に編集を諦めない。
- `PDFTextEditPlanner`が処理を自動選択する。表示用の説明文やユーザーが選ぶ編集モードを返さない。
- `PDFInternalTextEditEngine`が元文字の変更・除去を担当する。PDFiumのhandleは処理内だけで管理し、選択・保存時に原本から再照合する。
- `PDFTextRenderer`が確定したフォントと位置で新しい文字を描く。元文字を除去できた場合は透明な前景だけを加え、白い矩形を描かない。
- `PDFVisibleTextUnicodeWriter`が、本アプリで描いた文字の実コードとUnicodeの対応を保存する。CoreTextの文字・glyph・位置と、出力された可視文字の位置・書体・サイズを照合する。誤ったToUnicodeや欠落を見えないOCR文字で埋め合わせず、保存後の文字自体を再編集できる状態にする。
- `PDFExportEngine`が一時出力・再読込・構造検査・画素検査を終えてから出力先へatomicに配置する。画面プレビューもこの保存経路を通す。

## 自動選択の順序

1. 元のフォント資源に変更後の全文字があり、幅や描画状態を保持できる場合は、同じフォントで変更する。
2. 元のsubsetに新しい漢字が無い、または書体・サイズを指定した場合は、元の選択文字だけを除去し、CoreTextで確定した文字を透明な前景として加える。背景色の推定や白塗りは不要になる。
3. 元文字を安全に除去できない場合は従来互換の描画経路が残る。ただし内部編集の検証失敗を、その場で白塗りへ自動降格させて確定してはいけない。対応範囲外の改善は後述の順序で進める。

これらは内部の実装区分であり、画面のモードではない。文字の移動や既存の行再配置は従来経路として別に扱う。

## 部分範囲と文字間隔

PDFの一つの文字objectが日付全体を持っていても、選択範囲だけを変える。`TJ`の位置調整や`Tj`・`'`・`"`による表示を、文字列の単純な置き換えとして扱わない。保持する文字は元font・文字コード・実originで再構成し、前後の文字を移動しない。

削除は空文字への変更として元glyphを除去する。白い覆いを描かない。同じobjectへの非重複編集は元の座標に対する一つの計画へ集約する。範囲が重複する場合や、集約時に同じ書体を証明できない場合は、先の編集を黙って消さず確定を中止する。

複数のshow/objectに分かれた選択は、Unicode・bbox・実code・font・size・色・baselineから元範囲へ分割して除去する。利用者の編集は一件のまま管理する。矩形clipは、既知の単一矩形だけから成るchainがglyphの周囲を十分に含み、PDFiumでも実際のclipが残っていない場合だけ中立と判定する。文字を切るclipや未知のpathはこの判定へ混ぜない。

PDFiumのcontent生成はICCBased色や対象外の文字のUnicodeを保持できないケースがある。1ページ・既知のContents stream列・独立したshow末尾・直後がET、という条件を満たす場合は`PDFContentTextRemovalWriter.rewritingTextShows`で文字列operandだけを変更する。選択外のprefixと字間を保持し、同じfont内の一意な明示codeで置換するか、対象codeだけを除去する。背景・罫線・画像・ICC色指定・別streamは元のbyte列を保持する。対象文字をPDFiumで事前照合し、保存直後にも構造・対象外Unicode・origin・size・色を確認する。

この局所書換えでは、対象外のmarked辞書と直接Imageだけを配置するFormは元の命令を保持できる。対象Form内の文字・marked内の選択・文字や再帰Formを含むXObject・inline image・後続の相対配置へ影響するshow等は扱わない。その他の構造はPDFium経路で検証し、色・文字・位置が変わる場合は確定しない。PDFiumのglyph幅・path APIはUnicodeを引数に取り、文字設定APIの実charcodeとは分けて保持する（[公式実装](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/fpdfsdk/fpdf_edittext.cpp)を照合）。

## 出力の確認

PDFiumで保存して再openし、対象の文字・origin・サイズ・glyph幅、保持文字の位置、対象外page objectのgeometry・色・clip等を確認する。同じ文言が別の場所に残っていても、対象座標の変更を確認できればよい。

透明再描画後は、編集位置の可視文字から新しい文字を抽出できることも検査する。生成した日本語を保存して開き直し、別の漢字へ変更する往復を検証する。さらに同一CoreGraphicsレンダラーで変更前後を画像化し、編集対象領域外の差分を検出する。各ページの長辺は最大2048px、色差12以下を微差として扱い、領域外の変化は最大3pxまたは比較対象の0.01%までに制限する。これは文字/object照合に加える保護であり、画素検査だけで元文字の除去を証明しない。

編集の確定、再編集、undo/redo、書き出しが同じ原本と編集計画を使う。複数編集の検証が失敗したら入力・それまでの編集・既存出力を保持する。

## 調査から採用した考え方

- [PDFium編集API](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_edit.h)にはobject単位の挿入・除去・文字設定・content生成がある。視覚選択からobjectと文字範囲を特定する責任はアプリ側に残る。APIが成功しただけで編集成功としない。
- [Adobeの文字編集案内](https://helpx.adobe.com/acrobat/desktop/edit-documents/edit-text-in-pdfs/modify-text.html)は、文字を選んで入力する操作を中心にしている。元フォントの利用には条件もある。利用者の操作は簡単にし、フォント不足や保存方式の分岐はアプリ内で扱う。
- [PyMuPDFのページAPI](https://pymupdf.readthedocs.io/en/latest/page.html)は文字除去と画像・線画の処理を区別する。矩形で全要素を消す処理と、対象glyphだけの変更を混同しない。本アプリは現行PDFiumのまま文字objectの再構成を実装する。
- [LibreOffice PDF import](https://docs.libreoffice.org/sdext.html)のような文書モデルへ取り込む方式もあるが、再出力による文書全体の再解釈より、既存ページの局所変更を優先する。
- [pdf-libの公開README](https://github.com/Hopding/pdf-lib/blob/master/README.md)の描画・文書構成APIを、既存文字の安全な局所編集エンジンの代わりと見なさない。表示できる、文字を追加できる、元文字を編集できる、は別の責任である。

上記は2026-10-29確認、PDFiumのglyph APIは2026-10-30に公式実装も再確認。商用製品の内部実装を推測で断定しない。OSSの知名度やAPIの数で全PDFへの対応を保証しない。

## 継続して広げる順序

1. 原streamの局所書換えを複数ページ・より広い位置指定へ拡張する。page tree・共有資源・後続文字の位置への影響を先に証明する。複数show/objectに分割された選択の除去は今回実装済み。
2. 回転・Form XObject・marked contentを、共有資源の影響やタグの意味を保ったまま扱う。対応する生成fixtureと再open検査を先に用意する。
3. 元PDFにToUnicodeが無い、文字とglyphが一対一でない、画像や輪郭だけの文字を別々に扱う。本アプリが新規描画した既知の文字へのToUnicode付与と、未知の原文の復元は区別する。OCRで文字を得ることと、元の画像文字を消せることは分けて設計する。
4. 互換描画の白い覆いを、文字除去が証明できる経路へ順次置き換える。背景色のサンプリングは画像・グラデーション・罫線に一般化できないため最終解決にしない。

縦書き・アラビア語等の複雑な組版・段落全体の自動reflowは今回の対象に含めない。暗号化・権限制限・署名付き文書に対する既存の内部編集制限は維持する。元文字を通常の編集で取り除いても、metadataや過去revisionを含む秘匿情報の消去を保証するものではなく、墨消しは別機能として検証する。

生成fixtureはテストコード内で作成する。利用者の実PDF・抽出文字・画面画像は`tmp/`にだけ置き、GitやCIログへ含めない。
